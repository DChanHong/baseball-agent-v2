# Agent 50개 골든 데이터셋과 RAGAS 개선 비교 계획

> 작성일: 2026-10-06
> 상태: 사용자 합의된 계획. 50개 데이터셋 작성과 확대 평가는 아직 시작하지 않았다.
> 목적: 다른 세션이 이 문서를 읽고 데이터셋 구축부터 이어서 실행할 수 있도록 범위·순서·저장 계약을 고정한다.

## 1. 사용자와 합의한 방향

- 초기 점검용 12개 대신 다양한 50개 평가 사례를 만든다.
- 질문·기대답변·문서 버전을 고정하고 현재 agent의 기준선을 측정한다.
- 이후 리랭커 등의 변경을 동일한 데이터셋으로 비교한다.
- RAGAS 점수와 agent 기능 성공 여부를 별도로 기록한다.
- 전체 테스트와 결과 정리 후 블로그 초안을 작성한다. 리랭커 구현은 이 계획의 후속 비교 대상이며 현재 작업에 포함된 구현 요청은 아니다.

현재 요청은 이 계획을 Markdown으로 저장하는 것이다. 이 문서 작성만으로 유료 평가 실행, DB 변경, 커밋·push까지 수행하라는 요청으로 해석하지 않는다. 후속 세션은 사용자의 이어서 진행하라는 요청과 저장소 지침을 기준으로 실행한다.

## 3. 50개 평가셋 구성

50개는 고유 평가 사례 수다. 후속 질문 사례는 고정된 이전 대화와 평가 대상 마지막 turn을 함께 포함하며, 실제 API 호출 수는 50회보다 많을 수 있다.

| 영역 | 개수 | 포함할 주제 |
|---|---:|---|
| 구장 안내 | 15 | 교통, 주차, 반입, 음식물, 입장·재입장, 시설 |
| 예매 안내 | 10 | 공식 예매처, 예매 방법, 취소·환불, 구단별 차이 |
| 야구 지식 | 15 | 기본 정의, 판정 조건, 예외, 비슷한 규칙 구분 |
| 복합·후속 질문 | 5 | 여러 조건, 앞선 구장·경기 문맥, 질문 변경 |
| 근거 부족·범위 밖 | 5 | 없는 정보, 불명확한 질문, 단정하면 안 되는 요청 |
| **합계** | **50** | |

선정 규칙:

- 여러 구장·구단을 포함한다. 현재 DB에 있는 쉬운 문서만 골라 검색 누락을 숨기지 않는다.
- 단순 정의 외에 조건·예외, 비교·복합 질문, 짧은 구어체·동의어 표현을 섞는다. 표면 표현만 다른 질문으로 개수를 채우지 않는다.
- 정책의 기준일·행사 종류·구단 차이가 답변에 영향을 주는 사례를 포함한다.
- 기존 30개 기능 case와 초기 RAG 3개를 검토해 재사용하고 원래 ID와 연결한다. 기존 ID의 의미를 바꾸지 않는다.
- 골든셋의 다수는 RAG 검색·답변 평가에 사용한다. 일정 조회, 인증, Tool 오류, SSE 중단 등 agent 시스템 검증은 기존 기능 case와 합성 테스트로 보완한다.
- 모든 50개에 네 RAGAS 점수가 반드시 생기는 것은 아니다. 비RAG·근거 없음·fallback·문맥 직접 응답은 적용 가능 지표와 제외 사유를 명시한다.

## 4. 골든 후보의 데이터 계약과 검수

### 사례별 필수 필드

| 구분 | 기록할 내용 |
|---|---|
| 식별 | case ID, dataset version, category, 기존 case 연결 |
| 입력 | 합성 질문, 고정 대화 문맥, 필요한 날짜·선택 경기 조건 |
| 기대 동작 | 기대 Tool·filter, 답변 가능 여부, 확인 질문·거절 등 허용 동작 |
| 기대 내용 | reference answer, 필수 사실, 금지 주장, 조건·예외 |
| 출처 | 공식 원문 URL 또는 로컬 공개 원문 경로, locator, 확인일·기준일·hash |
| 검색 정답 | 관련 logical document/revision/chunk ID, 관련성 등급, 관련 근거 범위 |
| 검수 | status, reviewer kind, reviewed at, human_reviewed, 검수 메모 |
| 분할 | development 또는 held_out |

관련성 등급은 `0=무관`, `1=일부 도움`, `2=핵심 근거`로 시작한다. 질문별 관련 문서 수와 판단 이유를 기록한다. ID만 표시하지 말고 기대 사실과 근거 위치를 연결한다.

공식 원문에서 기대답변을 작성한 뒤 서비스 검색 결과와 대조한다. 모델이 만든 답변이나 현재 검색된 chunk를 그대로 정답으로 복사하지 않는다. 현재 corpus에 없는 핵심 사실도 출처에 근거해 기록하고, corpus gap으로 표시한다.

### 검수 상태

1. agent가 공식 출처와 조건·예외를 확인해 골든 후보를 작성한다.
2. 출처 충돌, 최신성 불명확, 정책 범위 불명확 사례는 별도 표시하고 확정 정답으로 승격하지 않는다.
3. 사람이 기대답변과 관련 문서 표시를 검수한 사례만 human-reviewed로 표시한다.
4. 사람 검수 전에도 명시적인 `agent_reviewed_candidate` 상태로 탐색용 기준선을 실행할 수 있지만, 이를 사람이 검수한 골든셋의 확정 품질 결과로 발표하지 않는다.
5. 기대답변과 검색 정답 검수 완료 후 `v1`을 고정한다. 변경 시 새 버전과 변경 사유를 남긴다.

### 개발용 35개 / 최종 확인용 15개

| 영역 | 개발용 | 최종 확인용 |
|---|---:|---:|
| 구장 안내 | 10 | 5 |
| 예매 안내 | 7 | 3 |
| 야구 지식 | 11 | 4 |
| 복합·후속 | 4 | 1 |
| 근거 부족·범위 밖 | 3 | 2 |
| **합계** | **35** | **15** |

동일 사실·같은 질문의 변형은 한 그룹으로 묶어 분할 간 누출을 줄인다. 최종 확인용은 변경이 확정된 시점에 평가하고 결과를 보며 반복 튜닝하지 않는다. 결과를 보고 튜닝했다면 그 사실을 남기고 이후 독립 확인용으로 간주하지 않는다. 두 그룹과 50개 전체를 각각 집계한다.

## 5. 측정 지표와 결과 해석

### RAGAS

| 지표 | 평가 입력과 의미 |
|---|---|
| Faithfulness | 실제 생성기에 전달한 근거로 모델 답변이 뒷받침되는지 |
| Answer Relevancy | 질문과 생성 답변의 관련성 |
| Context Precision | 원래 검색 순서 또는 리랭킹 후 순서의 근거 관련성 |
| Context Recall | 검수 reference의 사실을 검색 결과가 포함하는지 |

원래 retrieval 결과와 생성기에 실제 전달한 근거를 따로 수집한다. 서버가 덧붙인 출처·검수 안내 전의 모델 출력과 사용자에게 보인 최종 답변도 구분한다. 최종 문자열을 추정해 잘라 모델 출력으로 만들지 않는다.

기존 adapter의 제외 정책과 충돌하는 부분은 실행 전에 검토한다. 특히 후속 질문은 고정 문맥을 포함한 평가 입력 정의가 필요하다. 명시적인 scope·adapter version 없이 질문을 몰래 재작성하지 않는다.

### 검색 순위와 리랭커 평가

- `Recall@k`: 검수된 관련 근거 중 검색한 비율.
- `MRR@k`: 첫 관련 근거의 순위.
- `nDCG@k`: 관련성 등급을 반영한 상위 순위 품질.
- 우선 k는 3·5로 잡고 실제 서비스 top-k·후보 수를 확인해 평가 전에 확정한다.
- chunk 기준과 document 기준을 구분하고 중복 chunk 처리 규칙을 고정한다.
- 정답 관련 근거가 corpus에 없는 사례는 corpus coverage 실패로 별도 집계한다. 검색 성공 분모에서 제외한 건수도 함께 공개해 성능을 높게 보이게 만들지 않는다.
- 불완전한 relevance label에서 나온 Recall은 corpus 전체의 완전한 Recall이라고 주장하지 않는다. 평가 후보 pool과 검수 범위를 기록한다.

### Agent 동작과 비용

기대 Tool·입력·문맥 처리, 필수 사실·금지 주장, 답변 가능 여부, 계약 검증, fallback·timeout, SSE 완료, 저장·재조회 일치 여부를 기록한다. 시스템 완료와 질문 해결을 별도로 판정한다.

단계별 시간, 전체 요청 완료 시간, 토큰·비용, 리랭커 추가 지연도 남긴다. 포함 관계가 있는 단계 시간을 더해 전체 시간으로 사용하지 않는다. 표본이 적은 p95는 참고값임을 표시하고 성공 실행만의 시간과 전체 시도 시간을 구분한다.

단일 agent 종합 점수를 만들지 않는다. 영역·분할별 지표, 평가 가능 수, 제외·오류·미실행 수와 기능 결과를 함께 제시한다. 제외 점수는 null과 사유로 남기고 0점·1점으로 대체하지 않는다. 성공 답변만 비교하는 표에는 양쪽 모두 성공한 paired 표본 수와 전체 실패율을 같이 표시한다.

## 6. 실행 순서

1. **현황 확인:** 최신 revision, local 서비스 상태, corpus·migration 상태, 기존 case와 adapter·테스트를 읽는다. 환경 점검 결과를 기록한다.
2. **후보 50개 작성:** 위 분포에 맞춰 source-backed reference와 기대 동작을 작성한다. 중복·출처 충돌·corpus gap을 표시한다.
3. **검색 정답·분할 확정:** relevance label과 개발/최종 확인용 분할을 검수하고 dataset·corpus snapshot hash를 고정한다.
4. **재사용 가능한 runner 준비:** 이전 임시 harness에 의존하지 않도록 실제 API 결과 수집·RAGAS 실행·순위 지표·JSON 검증을 재실행 가능한 구조로 만든다. 새로운 dataset은 기존 manual schema에 억지로 맞추지 말고 별도 schema/validator 계약을 정한다.
5. **합성 검증:** 기존 backend 테스트와 평가 데이터 검증을 실행한다. Tool 오류·timeout·문맥·SSE·인증 처리는 우선 유료 호출 없이 확인한다.
6. **현재 기준선:** 실제 로컬 인증·DB·채팅 API로 50개를 1회씩 실행하고 적용 가능한 RAGAS를 측정한다. 기본 모델·timeout·생성 정책을 유지한다. 실패를 고친 뒤 기준선인 것처럼 저장하지 않는다.
7. **안정성 점검:** 사전에 고른 대표·경계 사례 10개를 2회 추가 실행하는 방안을 사용한다. 총 70개 case 실행 기준이며 다중 turn·judge 호출은 별도다. 실행 여부는 예산 산정 후 확정하고, 실패한 사례만 성공할 때까지 반복하지 않는다.
8. **결과 정리:** 영역·분할·case별 점수와 실패, 비용·시간·변동을 보고서에 정리한다. 대표 UI 완료·재열기 검증도 수행한다.
9. **향후 개선 비교:** 리랭커 등 변경을 하나씩 적용해 동일 데이터셋으로 비교한다. 개발용에서 결정한 뒤 최종 확인용을 실행한다.
10. **블로그:** 기준선 결과를 바탕으로 새 7번 초안을 작성한다. 개선을 아직 실행하지 않았다면 개선 효과를 썼다고 표현하지 않는다.

## 7. 리랭커 비교 시 고정할 조건

- 검색 비교: 같은 query embedding·corpus·filter·후보 pool을 사용해 원래 순서와 리랭커 순서를 비교한다. 후보 수 확대 효과와 순서 변경 효과를 분리한다.
- 답변 비교: 같은 질문·문맥·모델·prompt·reasoning·timeout·최종 근거 개수·길이 제한을 사용한다. 각 방식이 선택한 실제 근거를 수집해 RAGAS를 적용한다.
- baseline과 변경 run은 별도 파일로 남기고 `baseline_run_id`로 연결한다.
- corpus 보강, chunking 변경, 모델 변경을 리랭커와 동시에 섞지 않는다. corpus가 변경되면 새 corpus version에서 원래 방식과 개선 방식을 모두 다시 측정한다.
- query별 점수 차이와 개선·악화 사례, 답변 내용 검토, 추가 latency·비용을 함께 보고한다. 작은 표본의 점수 차이를 통계적으로 확정된 개선이라고 단정하지 않는다.

## 8. 비용·개인정보·환경 규칙

- 이전 12개 계획의 $1.00 상한은 50개 계획의 승인 예산으로 승계하지 않는다. 생성·judge·embedding·후속 turn·반복·온라인 평가까지 포함해 예상 호출량과 현재 단가를 산정한다.
- 유료 실행 전 예산과 중단 정책을 확정한다. 설정한 상한에 도달하면 중단하고 남은 case를 `not_run`과 사유로 기록한다. usage가 없는 취소 호출 비용은 0원으로 처리하지 않는다.
- offline 평가와 온라인 표본 평가가 의도치 않게 중복되지 않도록 검증 프로세스 설정을 관리한다. 온라인 연결 smoke는 대표 사례로 별도 기록하고 일반 서비스 설정은 바꾸지 않는다.
- 합성 질문과 공개 근거만 사용한다. 실제 사용자 대화, 사용자 ID, 운영 conversation/message ID, 이메일, 인증 header·cookie·token·key를 결과에 넣지 않는다.
- 합성 생성 답변과 평가 입력 전문은 임시 경로에만 두고 Git에는 점수·hash·설정·출처·요약을 남긴다. 원문 미보관 때문에 같은 생성 답변을 영구 재평가할 수 없다는 제한을 명시한다.
- local 환경과 별도 합성 계정을 사용하고 정리는 생성한 테스트 데이터 범위에 한정한다. DB 접속·migration·seed·reset, git 이력 변경은 루트 `AGENTS.md`와 해당 세션 사용자 승인을 따른다.
