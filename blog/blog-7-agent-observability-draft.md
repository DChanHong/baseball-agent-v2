# [AI Agent] 답변이 느린 이유를 찾기: 최소 Observability 구현

> 상태: 구현·합성 테스트·실제 모델 호출 관찰을 반영한 초안
> 작성일: 2026-10-05
> 로컬 앱과 운영 Supabase를 연결해 관찰한 4개 실행을 포함한다. 정식 평가 run과 전체 품질 평가는 후속 범위다.

채팅 로딩과 답변 생성 timeout을 고친 뒤, 다음 질문이 남았다.
응답이 늦어졌을 때 routing, 검색, 최종 답변 생성 중 어디에서 시간을 썼는가?

기존에도 각 모듈의 로그와 Tool card가 있었다. 하지만 서로 다른 요청이
동시에 실행되면 로그 순서만으로 같은 질문의 처리 과정을 묶기 어려웠다.
그래서 다음 기능을 늘리기 전에 실행 한 번을 연결하는 작은 trace를 만들었다.

## 1. 현재는 별도 관측 라이브러리와 SaaS가 필요하지 않다고 판단했다

첫 범위는 graph 실행 하나를 설명하는 것이다. Python 표준 logging에
`agent_trace` JSON 이벤트를 추가하고, 같은 실행의 이벤트에 임의 trace ID를
붙였다. 외부 수집 서비스와 별도 DB table은 추가하지 않았다.

현재 필요한 것은 한 요청에서 어떤 Tool이 실행됐고, 어느 단계에 시간을
썼으며, 왜 기본 답변으로 전환됐는지 확인하는 것이다. 이 범위에서는
표준 로그와 trace ID만으로 먼저 원인을 확인할 수 있다고 판단했다.
그래서 별도 관측 라이브러리나 SaaS를 붙이는 일은 지금 필요하지 않다고
결정했다. LangSmith, Langfuse, OpenTelemetry 등의 도입도 이번 범위에서 제외했다.

이미 사용하는 LangGraph와 LangChain은 유지한다. 새로 만든 계측에는 Python의
`logging`, `ContextVar`, `perf_counter`, `uuid4`, `json`을 사용했고, 관측을 위한
패키지는 추가하지 않았다. 외부 도구의 기능·비용을 비교 평가한 결론은 아니며,
현재 필요한 범위와 관리할 설정을 기준으로 내린 선택이다.

여러 서버의 로그를 모으거나, 많은 요청의 지연·실패율을 집계하거나,
대시보드와 알림이 필요해지면 도입을 다시 검토한다. 지금은 원인을 찾는 데
필요한 최소 정보를 확보하고 실제 실행으로 유용성을 확인하는 데 집중했다.

이 ID를 기존 assistant metadata에도 남겨 답변과 실행 로그를 연결했다.
사용자 ID나 질문 원문을 trace ID 대신 사용하지 않았다.

## 2. 무엇을 측정했는가

routing, Tool 실행, embedding, retrieval, answer와 answer LLM 호출의 시작·종료를
기록했다. 시간은 monotonic clock으로 측정하고 이벤트 시각은 UTC로 남겼다.

검색 결과에서는 chunk ID, distance, 결과 수를 기록했다. 이 정보는 검색
노이즈나 빈 결과를 확인하는 데 사용한다. 실제 query나 검색 문서 본문은
새 trace에 넣지 않았다.

Tool 시간에는 embedding과 검색 시간이 포함된다. answer 시간에도 모델 호출
시간이 포함된다. 이 값을 전부 더하면 중복 계산이 된다.

## 3. 완료와 성공을 구분하기

답변 모델이 timeout을 넘기면 기존 기본 답변으로 전환한다. 사용자는 응답을
받으므로 graph 실행은 완료됐지만, 모델 기반 답변 생성은 실패한 것이다.

따라서 `turn.completed`만 보지 않고 `answer_source=fallback`과
`fallback_reason=TimeoutError`를 함께 본다. Tool 예외 후 기본 답변으로
종료한 경우도 별도로 구분한다.

빈 검색도 비슷하다. 검색 실행 자체는 정상 종료됐지만 결과 수가 0일 수
있다. 또 결과가 있다는 사실만으로 질문에 충분히 답할 수 있다고 볼 수
없다. 검색의 결과 존재 여부와 최종 답변의 answerability를 구분했다.

## 4. 동시 실행과 개인정보

LangGraph는 node를 비동기 task에서 실행한다. trace ID는 graph state로 전달하고,
node 실행 안에서 ContextVar를 설정한 뒤 복원했다. 서로 다른 요청을
공유 mutable 변수 하나로 구분하지 않도록 했다.

새 trace에는 질문·답변·prompt·Tool payload 전문과 인증값을 넣지 않는다.
예외도 메시지 대신 타입만 기록한다. 이 정책은 새 trace의 범위이며 기존
HTTP body logging이나 exception logger 전체를 정비했다는 뜻은 아니다.

## 5. 무엇을 검증했는가

합성 테스트로 정상 RAG, 빈 검색, Tool 실패, 답변 timeout, 무도구 응답,
routing 실패를 검증했다. 동시 실행에서 ID가 섞이지 않는지와 consumer가
stream을 닫았을 때 중단 이벤트가 남는지도 확인했다.

질문·근거·답변·예외에 같은 합성 비공개 문자열을 넣고 새 trace JSON에는
그 문자열이 없는지 검사했다. 전체 backend 테스트는 78개가 통과했다.

이 테스트는 실제 모델·운영 DB를 사용한 응답 속도 측정과 구분한다.
합성 테스트로 기록 구조와 실패 처리를 확인한 뒤, 실제 앱에서도 trace가
원인 파악에 도움이 되는지 확인했다.

## 6. 실제 실행에서 찾은 지연과 fallback

로컬 frontend·backend를 운영 Supabase에 연결하고 실제 모델 호출을 수행했다.
사용자가 질문을 보낸 뒤 콘솔 로그에서 확인한 graph 실행은 4개였다.
질문과 답변 전문, 사용자 식별자, 인증 정보는 글에 옮기지 않고 처리 경로와
시간만 정리했다. 별도의 정식 evaluation run을 저장한 회차는 아니다.

| 처리 경로 | Routing | Tool | 최종 답변 단계 | 전체 graph 시간 | 결과 |
|---|---:|---:|---:|---:|---|
| 경기 조회 | 4.10초 | 0.10초 | 15.02초 | 19.24초 | 답변 모델 timeout 후 fallback |
| 선택 경기 context 직접 응답 | 3.41초 | 호출 없음 | 0.001초 미만 | 3.41초 | 직접 응답 완료 |
| 선택 경기 context 직접 응답 | 3.90초 | 호출 없음 | 0.001초 미만 | 3.90초 | 직접 응답 완료 |
| 야구 지식 RAG | 4.46초 | 2.86초 | 12.90초 | 20.23초 | 답변 검증 실패 후 fallback |

시간은 반올림한 값이다. 전체 graph 시간에는 node 전환 등의 시간도 포함된다.
HTTP 요청 시작부터 화면 표시까지의 사용자 체감 시간과는 다르다.

야구 지식 RAG의 Tool 시간을 나누면 embedding이 약 2.58초, DB 검색이
약 0.28초였다. 검색 결과는 5개였고 모델 호출도 약 12.90초 후 반환됐다.
하지만 최종 답변 검증에서 `ValueError`가 발생해 기본 답변으로 전환됐다.

Trace만으로 확인한 것은 검증 실패의 타입과 fallback 경로다. 구체적인
사유는 기존 backend 예외 로그를 대조해 확인했다. 답변 모델이 허용 목록에
없는 limitation을 반환한 것이었다. 모델 호출의 `answer_llm.completed`와
최종 답변의 성공을 같은 의미로 보면 이 문제를 놓칠 수 있다.

경기 조회도 Tool 실행은 약 0.10초로 끝났지만, 답변 모델이 15초 제한을 넘겨
fallback으로 종료됐다. 두 사례 모두 Tool 실패보다 답변 생성 단계가
대기 시간과 사용 가능한 답변에 영향을 줬다.

이번 네 실행만으로 서비스 평균 latency나 fallback 비율을 일반화할 수는 없다.
다만 관찰한 사례에서는 DB 검색보다 LLM routing과 최종 답변 생성이 지연의
대부분을 차지했다. 또한 약 20초를 기다린 뒤 모델 답변을 사용하지 못하는
사례를 확인했다. 최소 trace로 다음 개선 대상을 좁힐 수 있었다.

## 7. 이번 범위의 완료와 다음 작업

이번 로그 구현은 현재 단계에서 필요한 실행 경로와 시간, fallback 원인을
확인하는 기반으로 충분하다고 판단했다. 우선 여기서 관측 기능의 첫 회차를
마무리하고, 실제 로그에서 드러난 답변 생성 문제를 다음 작업으로 삼는다.

1. 허용되지 않은 limitation이 생성되는 입력·프롬프트·검증 계약을 점검한다.
2. 같은 평가 질문으로 입력 근거량, 출력 길이와 모델 설정을 비교한다.
3. 응답 시간뿐 아니라 답변 검증 통과 여부와 fallback 빈도도 함께 기록한다.
4. 완성된 답변을 나눠 보내는 현재 방식과 실제 토큰 streaming의 필요성을 검토한다.

Timeout을 늘리는 것만으로는 답변 속도를 개선할 수 없다. 기다린 모델 결과를
검증에서 버리는 원인을 먼저 줄이고, 품질을 유지하면서 시간을 줄이는지
동일한 평가 질문으로 확인한다. 이 개선들은 아직 구현하거나 검증하지 않았다.

현재 trace는 graph 실행에 한정된다. HTTP 처리, 답변 DB 저장과 SSE 전송
실패의 추가 계측, token usage와 운영 로그 보존 정책은 후속 범위다.
Step 3 전체가 끝났다는 의미가 아니라, 다음 문제를 찾는 데 필요한 최소
관측 기반을 실제 실행에서 확인했다는 의미로 기록한다.
