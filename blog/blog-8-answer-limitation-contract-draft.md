# [AI Agent] 로그를 보고 답변 생성을 개선하기: 계약 수정부터 모델·입력 비교까지

> 상태: 블로그 8~10의 내용을 합친 초안
> 작성일: 2026-10-05
> 앞 글: [답변이 느린 이유를 찾기: 최소 Observability 구현](blog-7-agent-observability-draft.md)
> 답변 계약 수정과 입력 정리 이후, 같은 모델의 추론 설정을 도구별로 조정해 구장·예매 안내 답변의 속도 개선을 확인했다. 야구 규칙의 추론량은 유지한다.

야구 직관 도우미를 만들면서 답변이 꽤 느리다는 것을 느꼈다. 그런데 느리다는 것만으로는 다음 작업을 결정하기 어려웠다. 검색이 오래 걸리는지, 모델이 오래 생각하는지, 아니면 결과를 처리하는 과정에서 문제가 생기는지 알 수 없었기 때문이다.

앞선 글에서는 한 요청의 routing, Tool 실행, embedding, retrieval, 답변 생성 과정을 trace ID로 연결했다. 이번에는 그 로그를 보고 발견한 문제를 수정하고, 실제 모델 호출로 변경 효과를 비교했다.

초기 모델 교체와 입력 축소 실험으로는 적용할 만한 속도 개선을 얻지 못했다. 이후 실제 추론 토큰을 측정하고 같은 모델의 설정을 도구별로 조정하자, 구장·예매 안내 답변의 중앙값이 12.25초에서 4.49초로 줄었다. 야구 규칙에서는 빠른 설정의 정확도 문제가 보여 기존 추론량을 유지했다. 로그를 남긴 뒤 어떤 판단과 변경으로 이어졌는지를 정리하려 한다.

## 1. 검색은 끝났는데 답변은 사용하지 못했다

처음 확인한 실제 실행 중 두 사례가 다음 작업의 출발점이 됐다.

| 처리 경로 | Routing | Tool | 최종 답변 단계 | 전체 graph 시간 | 결과 |
|---|---:|---:|---:|---:|---|
| 경기 조회 | 4.10초 | 0.10초 | 15.02초 | 19.24초 | 답변 모델 timeout 후 fallback |
| 야구 지식 RAG | 4.46초 | 2.86초 | 12.90초 | 20.23초 | 답변 검증 실패 후 fallback |

이 시간은 HTTP 요청부터 화면 표시까지의 시간이 아니라 graph 실행 시간이다. Tool과 답변 단계 안에 하위 단계가 포함되므로 모든 로그의 시간을 더해서 계산하지도 않았다.

야구 지식 RAG의 Tool 시간을 나누면 embedding은 약 2.58초, DB 검색은 약 0.28초였다. 검색 결과는 있었고, 답변 모델도 약 12.9초 후 결과를 반환했다. 하지만 서버 검증에 실패해 그 답변을 사용하지 못했다.

여기서 `answer_llm.completed`와 최종 답변의 성공이 다르다는 점이 드러났다. 모델 호출은 끝났지만 결과가 서버의 계약을 통과하지 못하면 기본 답변으로 전환된다. 사용자 입장에서는 약 20초를 기다리고도 생성된 답변을 받지 못한 것이다.

Trace에서는 검증 실패와 fallback 경로를 확인했고, 기존 예외 로그를 대조해 구체적인 원인을 찾았다. 모델이 서버의 허용 목록에 없는 limitation을 반환한 것이었다.

이 로그를 보고 DB 검색 최적화보다 최종 답변의 계약과 생성 시간을 먼저 점검하기로 했다.

## 2. 모델과 서버가 같은 허용 목록을 보도록 바꿨다

답변 모델에는 Tool의 `limitations`와 검색 근거가 전달되고 있었다. 서버는 여기에 검색 문서의 검수 상태, metadata의 제한사항, 본문 잘림 여부까지 반영해 허용 코드를 계산했다.

그런데 서버가 계산한 전체 목록을 모델 입력의 독립적인 필드로 전달하지는 않았다. 모델은 제공된 자료를 보고 제한사항을 표현해야 했고, 서버는 자신이 계산한 목록과 정확히 일치하는지 검사했다.

프롬프트에 원문 코드를 사용하라고 적는 것만으로는 이 차이를 충분히 드러내지 못했다. 출력이 `list[str]` 형태라고 해서 그 문자열이 허용된 코드라는 의미까지 보장되지는 않는다.

그래서 실제 전달할 근거를 구성한 뒤 전체 허용 목록을 계산해 `allowed_limitations`로 함께 전달하도록 바꿨다.

다음은 설명용 합성 예시다.

```json
{
  "limitations": ["ticketing_policy_may_be_outdated"],
  "allowed_limitations": [
    "needs_review",
    "ticketing_policy_may_be_outdated"
  ]
}
```

모델은 사용자에게 제한을 자연어로 설명하고, 구조화 필드에는 이 목록의 정확한 코드만 선택한다. 코드를 번역하거나 새로운 표현으로 바꾸지 않도록 했다. 근거가 부족하다는 뜻의 `insufficient_source`도 limitation 코드가 아니라 `answerability` 값이라는 점을 명시했다.

서버 검증은 유지했다. 잘못된 코드를 조용히 삭제해 답변을 통과시키거나, 실패하면 모델을 한 번 더 호출하는 방식은 적용하지 않았다. 입력에서 같은 계약을 보여주되, 출력이 계약을 어기면 기존처럼 거부한다.

이 변경은 모델이 잘못된 값을 절대 만들지 못하게 하는 장치는 아니다. 모델과 서버 사이에 있던 계약의 차이를 줄인 수정이다.

## 3. 다음 실패는 이유까지 구분할 수 있게 했다

기존 로그에서는 답변 검증이 `ValueError`로 실패했다는 사실을 볼 수 있었다. 다음 실행에서도 같은 범주의 문제가 반복되는지 확인하려면 더 구체적인 분류가 필요했다.

응답 반환 뒤에 `answer_validation` 단계를 추가하고 실패를 세 가지 코드로 구분했다.

| 실패 코드 | 의미 |
|---|---|
| `answer_schema_invalid` | 출력 구조나 필드가 계약에 맞지 않음 |
| `unknown_evidence_refs` | 전달하지 않은 근거를 참조함 |
| `unknown_limitation_codes` | 허용 목록에 없는 제한 코드를 반환함 |

이 코드는 최종 `fallback_reason`에도 남긴다. 모델이 생성한 원문 값이나 대화 전문을 새 trace에 복사하지 않고도 실패 종류를 확인할 수 있게 했다. Timeout은 별도로 `TimeoutError`로 구분한다.

합성 테스트에서는 허용 목록의 일치, 잘못된 코드와 근거 참조의 거부, 실패 후 fallback을 확인했다. 이 시점의 backend 전체 테스트는 92개가 통과했다.

후속 실제 비교에서 반환된 답변의 목록 밖 limitation 오류는 관찰되지 않았다. 다만 수정 전후를 같은 조건으로 비교한 실패율 실험은 아니므로, 이 결과로 오류가 몇 퍼센트 줄었다고 말하지는 않는다.

## 4. 빠른 모델을 비교했지만 적용하지 않았다

계약을 정리한 다음에는 최종 답변 생성 시간을 비교했다. 라우팅 모델과 답변 모델을 별도로 설정할 수 있도록 `OPENAI_ANSWER_MODEL`을 추가했다. 값이 없으면 기존 `OPENAI_MODEL`을 사용한다.

비교 질문은 병살, 보크, 사직야구장 예매, 주차, 그리고 자료가 없는 질문이었다. 공개 RAG 검색 결과를 한 번 수집해 고정하고 모델마다 각 질문을 3회씩 실행했다. 자료가 없는 질문에는 합성 빈 Tool 결과를 넣었다.

검색 결과가 실행마다 바뀌면 모델 차이와 검색 차이가 섞일 수 있기 때문에, 이번에는 답변 생성 서비스만 비교했다. 같은 prompt와 15초 제한을 사용했다.

| 답변 생성 측정 | 기존 gpt-5-mini | 후보 gpt-4.1-mini |
|---|---:|---:|
| 실행 횟수 | 15 | 15 |
| 생성·계약 검증 완료 | 11 | 15 |
| 시간 초과 | 4 | 0 |
| 전체 시도 중앙값 | 13.551초 | 1.440초 |
| 성공 시도만의 중앙값 | 11.823초 | 1.440초 |

후보는 분명 빨랐다. 하지만 계약 검증 통과는 내용의 정확성과 같지 않았다.

후보 답변에는 병살의 정의인 ‘하나의 연속된 플레이에서 두 개의 아웃’을 ‘두 명의 주자가 동시에 아웃’과 같이 바꾸는 표현이 있었다. 보크 설명에서는 판정 조건을 지나치게 일반화한 예시가 나왔다. `needs_review`를 구조화 필드에 넣었으면서 사용자에게 보이는 문장에서는 기준일이나 검수 필요 안내를 빠뜨리기도 했다.

정의의 범위를 유지하고 검수 안내를 반드시 문장에 넣도록 prompt를 보강해 후보를 15회 더 실행했다. 중앙값은 1.354초였지만 같은 종류의 내용 문제가 남았다.

그래서 모델 교체와 실험용 prompt 적용을 보류했다. 실제 설정은 기존 gpt-5-mini를 유지한다. 빠른 응답을 얻는 것과 서비스에 적용할 수 있는 답변을 얻는 것은 따로 확인해야 했다. 기존 모델에도 일부 안내 누락이 있었으므로 기존 모델의 품질이 완벽하다는 뜻도 아니다.

## 5. 기존 모델을 유지하고 입력을 줄였다

다음에는 모델을 바꾸지 않고 입력을 정리했다.

검색 결과의 metadata에는 검색 키워드, 예시 질문, 언어, 대상 독자와 분류 정보가 함께 들어 있었다. 이 항목들을 최종 답변 입력에서 제외했다.

본문, 출처, 기준일, 검수 상태, 제한사항, 원문 페이지와 시즌 정보는 그대로 남겼다. 예매 URL과 지하철 정보처럼 답변에 필요한 도메인 metadata도 보존했다. 검색 결과 수와 순서, 근거 참조도 바꾸지 않았다.

본문을 다시 요약하거나 관련성이 낮아 보이는 문서를 자동으로 버리지는 않았다. 정확도를 걱정하는 상황에서 우선 정보 손실 범위를 작게 유지하려는 선택이었다.

입력 JSON 문자 수는 다음처럼 줄었다. 이 비율은 토큰 수나 API 비용 감소율과 같지는 않다.

| 질문 | 변경 전 | 변경 후 | 입력 문자 감소 |
|---|---:|---:|---:|
| 병살 | 2,156 | 1,953 | 9.4% |
| 보크 | 16,581 | 15,932 | 3.9% |
| 사직 예매 | 1,550 | 1,534 | 1.0% |
| 사직 주차 | 1,674 | 1,432 | 14.5% |
| 근거 없음 | 278 | 278 | 0% |

기존 모델로 변경 전후 각각 15회 실행한 결과는 다음과 같다. 앞의 모델 비교와는 별도 실행이므로 기존 모델의 숫자가 다르다.

| 답변 생성 측정 | 변경 전 | 변경 후 |
|---|---:|---:|
| 실행 횟수 | 15 | 15 |
| 생성·계약 검증 완료 | 12 | 14 |
| 시간 초과 | 3 | 1 |
| 전체 시도 중앙값 | 11.886초 | 12.042초 |
| 성공 시도만의 중앙값 | 11.445초 | 11.738초 |

입력은 줄었지만 답변 속도는 개선되지 않았다. 시간 초과는 이번 표본에서 줄었지만, 작은 표본 한 번으로 안정성이 개선됐다고 확정하기는 어렵다. 입력이 동일한 ‘근거 없음’ 질문에서도 시간이 흔들렸다.

생성 답변의 핵심 내용은 점검했지만 검수 안내 누락과 일부 규칙 예시의 불명확한 표현도 남았다. 입력을 보존하는 테스트를 통과한 것만으로 생성 답변의 정확성까지 보장할 수는 없었다.

입력 정리는 코드에 반영했다. 다섯 fixture의 본문·근거 순서·제한 계약 보존을 확인했고, backend 전체 테스트는 98개가 통과했다. 이 변경은 입력을 정리한 작업으로 기록하고 latency 개선으로 분류하지 않았다.

## 6. 입력 크기 다음에는 추론 토큰을 봤다

입력만 조금 줄여서는 지연이 해결되지 않았다. 이번에는 모델이 반환하는 토큰 사용량을 읽어 input, output, reasoning, cached input 토큰 수를 trace에 추가했다. 숫자 counter만 남기고 답변이나 추론 전문은 로그에 넣지 않았다.

기존 호출에는 reasoning effort를 지정하지 않았다. [공식 GPT-5 문서](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_new_params_and_tools)를 확인한 뒤, 같은 gpt-5-mini의 `medium`과 `low`를 비교했다. 추론량을 낮추는 것은 정확도에 영향을 줄 수 있으므로 모델 이름이 같다는 이유로 바로 적용하지 않았다.

첫 30회 비교에서는 답변 시간 중앙값이 10.00초에서 4.83초로 줄었다. 추론 토큰 중앙값도 1,024에서 256으로 줄었다. metadata 축소보다 추론 설정 변화에서 시간 차이가 뚜렷했다.

하지만 보크 답변에서 와인드업과 세트 포지션의 정지 조건을 섞는 사례가 다시 나왔다. 그래서 모든 답변에 low를 적용하는 방식은 제외했다.

최종 정책은 다음처럼 정했다.

- 구장·예매 안내의 근거 정리: 같은 gpt-5-mini의 low 사용
- 야구 규칙과 그 밖의 Tool 답변: medium 유지
- 라우팅 모델과 추론 설정: 기존 동작 유지

검수 안내 누락은 모델의 선택에만 맡기지 않도록 바꿨다. 서버가 실제 사용한 needs_review 근거의 기준일과 검수·공식 출처 재확인 안내를 최종 답변에 붙인다. 먼저 기존 출력 계약을 검증하고, 안내를 붙인 결과도 길이 등의 schema를 다시 검사한다. 본문의 사실 설명은 여전히 모델이 담당한다.

최종 코드에서 같은 prompt와 근거로 비교한 구장 안내 세 질문의 결과는 다음과 같다. 각 설정으로 세 번씩, 총 9회씩 실행했다.

| 구장·예매 안내 답변 생성 | medium | low |
|---|---:|---:|
| 호출 수 | 9 | 9 |
| 생성·계약 검증 완료 | 7 | 9 |
| 시간 초과 | 2 | 0 |
| 전체 시도 중앙값 | 12.251초 | 4.491초 |
| 성공 호출의 추론 토큰 중앙값 | 960 | 256 |

이 범위에서는 중앙값이 약 **63.3% 줄었다.** timeout까지 기다린 시간을 포함한 값이며 전체 채팅의 화면 표시 시간과는 구분한다. 작은 표본과 API 변동도 있으므로 운영 전체의 평균 개선율로 일반화하지 않는다.

실제 기본 설정으로 다섯 질문을 세 번씩 다시 실행했다. 안내 답변 9회는 모두 low로 처리됐고 중앙값은 4.275초였다. 예매처를 유지하고, 주차 가능 대수 같은 미확인 정보를 만들어내지 않으며, 근거가 없는 질문에는 확인 불가로 답하는지 점검했다. 검수 대상 답변에는 서버 안내가 포함됐다.

야구 지식 6회는 medium으로 처리됐고 그중 한 번은 timeout이었다. 이 부분의 지연은 여전히 남아 있다. 야구 규칙의 정확도를 희생하면서 모든 질문이 빨라졌다고 쓰지는 않는다.

도구별 체인 선택, 토큰 로그의 비공개 원문 제외, 검수 안내와 parser 오류 처리를 포함해 backend 전체 113개 테스트가 통과했다. 모델 교체 없이 안내 답변의 생성 시간을 줄이는 변경은 코드의 기본 정책에 반영했다.

## 7. 로그를 남긴 뒤 달라진 것과 남은 과제

이번에 바뀐 것은 답변 생성의 입력·검증 계약과 문제를 판단하는 방식이다.

처음에는 ‘응답이 느리다’는 증상만 있었다. 로그를 연결한 뒤에는 검색이 끝났는데 답변을 버리는 경우, 모델 시간이 제한을 넘기는 경우, 출력 형식은 맞지만 내용에 문제가 있는 경우를 나눠 볼 수 있었다. 그 차이를 기준으로 계약을 수정하고 실험의 적용 여부를 결정했다.

관측을 위해 별도 라이브러리나 SaaS를 붙이지는 않았다. 기존 Python logging과 작은 trace로 지금 필요한 실행 경로와 실패 원인을 확인할 수 있다고 판단했다. 이미 사용 중인 LangGraph와 LangChain은 유지했다. 여러 서버의 로그 집계, 대시보드, 알림이 필요해지면 외부 관측 도구를 다시 검토하려 한다.

구장·예매 안내의 답변 생성 시간은 줄였지만, 전체 HTTP·DB 저장·SSE·브라우저 표시 시간을 포함한 개선율은 아직 측정하지 않았다. 야구 규칙의 지연과 세부 설명 품질도 다음 과제로 남는다. 이제 토큰 사용량과 단계 시간을 함께 보면서 이 범위를 더 좁혀갈 수 있다.

로그를 통해 답변 계약의 차이를 찾았고, 효과가 없던 입력 축소 실험도 확인했다. 마지막에는 추론 토큰을 근거로 속도를 줄이되, 정확도 문제가 나온 야구 규칙은 기존 설정으로 남겼다. 다음 개선도 같은 질문에서 내용과 시간을 함께 확인하면서 이어가려 한다.
