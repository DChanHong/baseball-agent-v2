# [AI Agent] 생성된 답변을 버리지 않기: limitation 계약 맞추기

> 상태: 코드와 합성 테스트 기반 초안
> 작성일: 2026-10-05
> 실제 모델의 수정 전후 실패율·응답 품질 비교는 후속 실행 후 추가한다.

최소 trace를 넣고 실제 질문을 실행하자, 검색이 성공해도 모델 답변을
사용하지 못하는 사례가 보였다. 야구 지식 검색의 DB 조회는 약 0.28초였고,
답변 모델은 약 12.9초 뒤 반환됐다. 하지만 검증에 실패해 기본 답변으로
전환했다. 전체 graph 실행은 약 20.23초였다.

문제는 허용 목록에 없는 limitation이었다. 이 관찰을 계기로 timeout이나
모델을 먼저 바꾸기 전에, 모델과 서버가 같은 출력 계약을 이해하는지 확인했다.

## 1. 서버가 알고 있던 목록

답변 입력에는 Tool의 limitations와 검색 evidence가 들어간다.
서버는 여기에 실제 전달된 evidence의 검수 상태, metadata의 제한사항,
본문 잘림 여부를 반영해 허용 코드를 계산했다.

모델에게는 이 전체 허용 목록을 독립적인 필드로 전달하지 않았다.
프롬프트는 원문 코드를 사용하라고 지시했지만, 출력 필드는 list[str]였다.
문자열이라는 형식은 맞아도 서버가 허용하는 코드라는 의미까지 보장하지는 않았다.

이 차이가 실제 오류의 유일한 원인이라고 단정할 수는 없다. 다만 입력 계약을
명확히 맞추는 것이 먼저 해결할 수 있는 문제였다.

## 2. 선택 목록을 입력으로 전달하기

서버가 bounded evidence를 만든 다음 허용 코드를 계산해
`allowed_limitations`로 전달하도록 바꿨다. Tool의 원래 limitations는 유지하고,
서버가 검증할 전체 목록을 별도 필드로 제공한다.

다음은 실제 사용자 데이터가 아닌 설명용 합성 예시다.

```json
{
  "limitations": ["ticketing_policy_may_be_outdated"],
  "allowed_limitations": ["needs_review", "ticketing_policy_may_be_outdated"]
}
```

모델은 이 목록에서 답변에 반영한 코드만 선택한다. 사용자에게는 한계를
자연어로 설명하지만 metadata에는 코드를 번역하거나 요약하지 않는다.
허용 목록이 비었거나 반영할 코드가 없으면 빈 목록을 반환하도록 명시했다.
answerability 값인 insufficient_source를 limitation 코드로 만드는 것도 금지했다.

이 구현은 요청마다 enum schema를 만드는 방식은 아니다. 입력과 prompt로
선택 목록을 제시하고, 서버 검증이 목록 밖의 값을 계속 거부한다.
따라서 잘못된 출력이 절대 발생하지 않는다는 보장은 없다.

## 3. 검증을 유지한 이유

모델이 새 코드를 반환하면 그 값을 지우고 답변을 통과시키는 방법도 생각할
수 있다. 하지만 제한사항 기록을 조용히 누락시키면 검증의 의미가 약해진다.
이번에는 기존 엄격한 검증과 fallback을 유지했다.

추가 모델 재시도도 붙이지 않았다. 이미 오래 걸린 응답에 호출을 더하는
것보다 한 번의 입력·출력 계약을 명확히 하는 데 집중했다.

## 4. 모델 반환과 검증 성공을 구분하기

기존 trace에서는 답변이 ValueError로 fallback했다는 것까지 보였다.
이제 실패 종류를 다음 코드로 구분한다.

- `answer_schema_invalid`: 출력 구조 또는 필드 검증 실패
- `unknown_evidence_refs`: 전달하지 않은 근거를 사용했다고 반환
- `unknown_limitation_codes`: 허용 목록에 없는 코드를 반환

응답 반환 뒤의 검증을 `answer_validation` 단계로 추가했다.
시간과 근거 수·허용 코드 수를 기록하고, 모델이 만든 원문 값은 오류 로그에
복사하지 않는다. 최종 fallback_reason도 이 코드로 남긴다.

Chain 내부에서 Pydantic 검증이 먼저 실패하면 별도 검증 단계에 진입하지
않을 수 있다. 이 경우에도 최종 fallback은 schema 오류로 분류한다.
Timeout은 기존 TimeoutError 분류를 유지한다.

## 5. 무엇을 확인했는가

합성 테스트로 Tool 코드, needs_review, metadata 제한과 content_truncated가
모델에 전달되는 목록과 서버 검증에서 일치하는지 확인했다.
상위 3개 밖의 근거가 허용 목록을 늘리지 않는지도 검사했다.

새 코드, 자연어로 변형한 코드와 잘못된 evidence ref는 여전히 거부한다.
출력 구조가 잘못됐을 때도 fallback으로 종료하고, trace에는 실패 코드가
남는다. 기존 timeout, 동시 요청 격리와 SSE 흐름 회귀도 검증했다.
Backend 전체 테스트는 92개가 통과했고, 이 회차에서 14개 사례를 추가했다.

이 테스트는 모델 출력을 fake chain으로 제어한 검증이다. 실제 모델의
실패율이 감소했거나 자연어 답변 품질이 개선됐다는 증거는 아니다.

## 6. 다음 검증

다음에는 같은 평가 질문으로 실제 모델 응답을 다시 확인한다.
검증 통과 여부와 latency뿐 아니라, 필요한 한계를 답변에 표현했는지
사람이 함께 검토한다. 빈 acknowledged_limitations로 통과한 것만으로
좋은 답변이라고 평가하지 않는다.

이번 회차에서는 모델, timeout, 검색 방식과 streaming을 바꾸지 않았다.
계약 수정의 효과를 먼저 확인한 뒤, 입력 근거량과 출력 길이·모델 설정을
비교해 지연을 줄이는 작업으로 이어간다.
