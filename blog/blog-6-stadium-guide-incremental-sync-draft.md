# [AI Agent] RAG 데이터를 운영하기: 전체 재임베딩에서 증분 갱신으로

> 상태: 구현 전후 내용을 채우기 위한 초안 템플릿
> 기준 spec: `docs/spec/2026-09-10-stadium-guide-incremental-sync-spec.md`
> 작성 원칙: 실제 수집·평가·운영 결과가 나오기 전에는 결과 수치와 성공 여부를 확정하지 않는다.

## 개요

KBO Mate의 구장 안내 데이터는 공식 출처를 정리한 normalized 문서를 임베딩하고 Supabase pgvector에 저장하는 방식으로 시작했습니다.

첫 구현에서는 전체 문서를 다시 임베딩한 뒤 `document_id`와 `chunk_id`를 기준으로 upsert했습니다. 데이터가 작고 임베딩 흐름을 처음 검증할 때는 충분한 방식이었지만, 실제 운영을 생각하면 몇 가지 문제가 생깁니다.

```text
내용이 바뀌지 않은 문서도 다시 임베딩한다.
새 문서와 변경된 문서를 구분하지 않는다.
출처에서 사라진 정보를 어떻게 처리할지 기준이 없다.
수집 실패를 정보 삭제로 오인할 수 있다.
새 데이터가 잘못돼도 기존 정상 데이터를 안전하게 유지할 방법이 없다.
```

이번 글에서는 구장 안내 RAG를 전체 재생성 방식에서 신규·변경·삭제 후보를 구분하는 증분 갱신 구조로 바꾸는 과정을 정리합니다.

## 1. 실사용 QA가 데이터 갱신 문제로 이어졌다

이 작업의 시작은 새로운 기능 요청이 아니라 실사용 QA에서 발견한 질문이었습니다.

```text
고척돔 음식물 반입 가능해?
```

Tool은 구장 안내 문서를 검색했지만, 기존 근거는 주류, 캔, 병, PET 음료 제한을 설명할 뿐 외부 음식물 반입 가능 여부를 직접 뒷받침하지 못했습니다.

처음에는 부족한 문서를 찾아 수정하고 다시 임베딩하면 된다고 생각할 수 있습니다. 하지만 같은 방식으로 구장 정보가 바뀔 때마다 전체 문서를 다시 처리하면 운영 과정은 점점 불안정해집니다.

그래서 질문을 바꿨습니다.

```text
부족한 문서 하나를 어떻게 추가할까?
↓
공식 정보가 계속 바뀌는 상황에서 RAG 데이터를 어떻게 안전하게 운영할까?
```

## 2. 저장소의 문서와 실제 vector index는 같지 않았다

작업 전 저장소에는 다음 데이터가 있었습니다.

```text
9개 구장
구장별 normalized 문서 5개
총 45개 embedded input
공식 출처 registry 55개
```

하지만 로컬 DB를 확인하니 실제 `rag_documents`와 `rag_chunks`에는 사직구장 데이터 5개만 존재했습니다.

```text
저장소의 embedded input: 45개
로컬 DB의 실제 embedding chunk: 5개
```

파일이 존재한다고 해서 검색 DB에도 반영됐다고 볼 수 없었습니다. 이후부터는 다음 세 상태를 분리해서 확인해야 했습니다.

```text
normalized 문서가 있는가
embedding 입력이 만들어졌는가
실제 DB에서 활성 검색 데이터로 제공되는가
```

## 3. 무조건 upsert만으로 부족했던 이유

기존 스크립트에도 upsert는 있었습니다.

```text
chunk JSONL 읽기
→ 모든 embedding_text 임베딩
→ rag_documents upsert
→ rag_chunks upsert
```

같은 ID가 들어오면 row를 갱신할 수 있지만, 운영에서 필요한 판단까지 해주는 것은 아니었습니다.

```text
이 문서가 처음 추가된 것인가?
기존 내용이 실제로 변경됐는가?
본문은 같고 embedding 모델만 달라졌는가?
공식 출처에서 정보가 정말 삭제됐는가?
단순 수집 실패인가?
```

upsert는 저장 방법이고, 갱신 파이프라인에는 그 전에 변경을 분류하는 단계가 필요했습니다.

## 4. 변경을 다섯 가지 상태로 분류했다

파이프라인의 기본 분류는 다음과 같이 정했습니다.

| 분류 | 의미 | 처리 |
|---|---|---|
| `CREATE` | 기존 활성 문서가 없음 | 신규 revision 후보 생성 |
| `UPDATE` | 기존 문서와 content hash가 다름 | 변경 revision 후보 생성 |
| `UNCHANGED` | 내용과 embedding 설정이 동일 | 임베딩과 DB 쓰기 생략 |
| `DELETE_CANDIDATE` | 정상 수집에서 기존 정보 소실이 반복 확인됨 | 검수 후 비활성화 후보 생성 |
| `MANUAL_REQUIRED` | 수집이나 정규화를 신뢰하기 어려움 | 사람이 직접 확인 |

embedding 모델이나 입력 규칙이 바뀌는 경우에는 별도로 `RE_EMBED`를 사용합니다. 이번 작업에서는 기존 `text-embedding-3-small`, 1536차원을 유지합니다.

## 5. 완전 자동 대신 반자동을 선택했다

공식 페이지에서 데이터를 가져왔다고 바로 서비스에 반영하지 않습니다.

```text
공식 페이지 수집
→ 이전 원문과 변경 비교
→ LLM이 normalized 후보 작성
→ 사람이 문서 단위로 검수
→ 승인
→ 로컬 반영과 검색 평가
→ 운영 반영
```

수집과 변경 감지는 자동화하지만, LLM이 작성한 후보를 승인하는 과정은 사람이 담당합니다.

구단과 시설 페이지는 구조가 서로 다르고, 메뉴나 광고 문구가 본문으로 섞일 수 있습니다. 공식 페이지라는 이유만으로 추출 결과까지 정확하다고 볼 수 없기 때문입니다.

관리자 화면과 cron도 이번 범위에 넣지 않았습니다. 터미널에서 직접 실행하되, 나중에 실행 주체가 바뀌어도 사용할 수 있도록 멱등성, 실행 이력, 실패 복구를 갖춘 명령으로 만듭니다.

## 6. 기존 데이터를 지우지 않고 revision으로 교체한다

새 문서를 검수하는 동안에는 현재 서비스 중인 데이터를 유지합니다.

```text
현재 활성 revision 유지
→ 새 revision 후보 생성
→ 검수와 승인
→ 로컬 평가
→ 새 revision 활성화
→ 이전 revision 비활성화
```

문서 ID도 날짜가 포함된 ID 하나로만 관리하지 않고 논리 문서와 revision을 분리했습니다.

```text
logical_document_id: GOCHEOK_stadium_food_guide
revision_id: GOCHEOK_stadium_food_guide_r0001
chunk_id: GOCHEOK_stadium_food_guide_r0001_chunk_000
```

하나의 논리 문서에는 활성 revision이 하나만 존재합니다. 이전 revision과 embedding은 롤백을 위해 보존하지만 일반 검색에서는 제외합니다.

## 7. 삭제는 즉시 실행하지 않는다

공식 페이지에서 문장이 보이지 않는다고 바로 데이터를 삭제하면 안 됩니다.

```text
HTTP 오류
빈 페이지
로그인 화면
접근 차단
JavaScript 렌더링 실패
페이지 개편으로 parser가 본문을 찾지 못함
```

이런 상황은 정보 삭제가 아니라 수집 실패입니다.

정상 수집 결과에서 같은 정보가 두 번 연속 사라졌을 때만 `DELETE_CANDIDATE`를 만듭니다. 이후에도 사람이 승인해야 현재 revision을 비활성화합니다. raw 원문과 revision 이력은 삭제하지 않습니다.

## 8. 공통 KBO 정책과 구장별 정책을 분리한다

KBO SAFE 캠페인처럼 전체 구장에 공통으로 적용되는 정책을 구장마다 복사하면 변경 시 여러 문서를 다시 갱신해야 합니다.

그래서 공통 정책은 `stadium_id=null`인 문서로 관리합니다.

```text
KBO_common_stadium_bag_policy
→ KBO 전체 구장 공통 반입·안전 기준

GOCHEOK_stadium_bag_policy
→ 고척스카이돔의 추가 제한과 예외
```

검색할 때는 해당 구장 문서와 공통 문서를 함께 조회하며, 같은 주제에서는 구장별 정책을 우선합니다.

## 9. 문서 유형도 질문의 의미에 맞게 확장했다

기존에는 반입 정책 문서가 음식물, 음료 용기, 주류 제한을 함께 담당했습니다. 이번에는 질문의 의미를 더 명확히 구분하기 위해 세 유형을 추가했습니다.

```text
stadium_food_guide
→ 외부 음식 반입, 취식, 구장 내 식음 매장

stadium_entry_guide
→ 게이트, 입장 시간, 티켓 확인, 재입장, 입장 동선

stadium_accessibility_guide
→ 휠체어석, 장애인 주차, 엘리베이터, 접근 가능한 출입구
```

예를 들어 캔·병·주류 제한은 `stadium_bag_policy`, 외부 음식 반입은 `stadium_food_guide`에서 다룹니다.

모든 구장에 문서 8개를 강제로 만들지는 않습니다. 공식 근거가 있는 유형만 생성하고, 없는 정보는 `missing_source`로 관리합니다.

## 10. Phase 1: revision 기반을 먼저 만들었다

첫 단계에서는 수집기보다 데이터를 안전하게 교체할 기반을 먼저 만들었습니다.

구현 내용:

```text
rag_documents에 logical_document_id와 revision_number 추가
활성 revision 상태와 활성화·비활성화 시점 추가
기존 문서를 위한 legacy_unreviewed 상태 추가
논리 문서별 활성 revision 하나만 허용
수집 실행, 출처 확인, 변경 후보, 배포 이력 테이블 추가
활성·승인 revision만 검색하도록 retriever 변경
stadium_id가 null인 공통 문서 검색 지원
신규 문서 유형의 routing schema와 Tool 설명 추가
```

기존 로컬 데이터는 서비스를 중단하지 않도록 legacy 활성 revision으로 전환했습니다.

검증 결과:

```text

관리 테이블: 4개
legacy 활성 revision: 5개
중복 활성 revision: 0개
공통 문서 검색 transaction: 통과
후보 데이터 쓰기와 rollback: 통과
Supabase schema lint: 오류 없음
백엔드 API 테스트: 59개 통과
```

관련 커밋:

```text
9a02068 feat: add stadium guide revision foundation
```

## 14. 로컬 평가를 통과해야 운영에 반영한다

운영 승격 전에는 변경 영역 평가와 전체 회귀 평가를 모두 실행합니다.

고척 음식물 반입 평가 예시:

```text
고척돔 음식물 반입 가능해?
고척돔에 외부 음식 가져가도 돼?
고척돔에 캔이나 병을 가져갈 수 있어?
고척돔에서 술을 반입할 수 있어?
고척돔 PET 음료 제한이 어떻게 돼?
```

필수 평가가 하나라도 실패하면 운영 승격을 막습니다. 평가를 무시하는 강제 옵션은 만들지 않습니다.

### 평가 결과

```text

변경 영역 passed:
공통 회귀 case 수:
공통 회귀 passed:
```
