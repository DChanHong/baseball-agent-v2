# [AI 에이전트] KBO 직관 플래너 Agent 서비스/MVP 명세 정리

이번 글은 KBO 직관 플래너 Agent를 구현하기 전에 정리한 서비스 명세와 MVP 범위를 기록한 글입니다.

처음부터 코드를 작성하기보다, 먼저 이 Agent가 어떤 문제를 해결해야 하는지, 어떤 사용자를 대상으로 하는지, 어떤 정보는 Tool로 조회하고 어떤 정보는 RAG로 검색해야 하는지 정리했습니다.

AI Agent를 만들 때 가장 먼저 정해야 하는 것은 "LLM을 어디에 붙일 것인가"가 아니었습니다.

더 중요한 질문은 이것이었습니다.

```text
이 문제가 정말 Agent가 필요한 문제인가?
사용자의 요청에 따라 실행 경로가 달라지는가?
Tool을 어떤 기준으로 나눌 것인가?
정확해야 하는 정보와 설명형 정보는 어떻게 분리할 것인가?
MVP에서는 어디까지 만들고 어디부터는 제외할 것인가?
```

이번 프로젝트에서는 이 질문에 답하기 위해 KBO 야구 직관을 준비하는 사용자를 위한 Agent를 기획했습니다.

## 1. 서비스 한 문장 정의

이 서비스는 야구 입문자와 직관 초보자가 응원할 팀과 관람할 경기를 찾고, 구장 기본 정보, 예매, 응원, 좌석 선택, 관람 팁을 단계적으로 준비하도록 돕는 KBO 직관 Agent입니다.

초기 제품의 중심은 `직관 정보 찾기`입니다.

야구 규칙이나 팀 역사 같은 일반 야구 정보도 중요하지만, MVP에서는 사용자가 실제로 관람할 경기를 찾고 준비하는 경험을 우선합니다.

즉 첫 번째 목표는 이런 질문에 답하는 것입니다.

```text
오늘 롯데 경기 있어?
다음 주말 서울에서 볼 수 있는 경기 찾아줘.
잠실야구장 위치 알려줘.
사직구장 처음 가는데 뭐 챙겨야 해?
롯데 홈경기 예매는 어디서 해?
보크가 뭐야?
```

## 2. 대상 사용자

이 Agent의 주요 사용자는 야구를 아주 잘 아는 팬보다, 직관 준비 과정에서 정보를 하나씩 찾아봐야 하는 사용자입니다.

대상 사용자는 다음과 같이 잡았습니다.

```text
야구 규칙, 용어와 관람 방법이 아직 익숙하지 않은 입문자
아직 응원할 팀을 정하지 못한 사용자
처음으로 원하는 팀의 경기를 직관하려는 팬
특정 날짜나 기간에 볼 수 있는 경기를 찾는 팬
익숙하지 않은 구장으로 원정 직관을 가는 팬
예매 방법, 응원 구역, 좌석 선택이 어려운 팬
```

이 사용자는 단순히 경기 일정만 알고 싶은 것이 아닙니다.

경기 일정, 구장, 예매, 응원, 준비물, 좌석, 날씨 같은 정보를 이어서 확인하고 싶어 합니다.

그래서 하나의 검색창보다 대화형 Agent가 더 자연스러운 형태라고 판단했습니다.

## 3. 해결하려는 문제

KBO 직관을 처음 준비하는 사용자는 여러 사이트를 오가야 합니다.

경기 일정은 KBO나 구단 페이지에서 확인해야 하고, 구장 위치와 좌석 정보는 구장 안내 페이지를 봐야 합니다.

예매는 구단마다 예매처와 방식이 다르고, 반입 정책이나 교통 안내도 구장마다 다릅니다.

초보자 입장에서는 다음 질문들이 한 흐름 안에 있습니다.

```text
내가 볼 수 있는 경기가 있는가?
어느 구장에서 하는가?
그 구장은 어떻게 가는가?
무엇을 챙겨야 하는가?
예매는 어디서 하는가?
어느 좌석이 나에게 맞는가?
야구 규칙 중 모르는 부분은 무엇인가?
```

이번 Agent가 해결하려는 문제는 이 정보를 사용자가 직접 흩어진 출처에서 찾지 않도록 돕는 것입니다.

기획 문서에서는 사용자 문제를 다음처럼 정리했습니다.

```text
1. 야구 규칙, 용어, 포지션과 경기 관람 방법을 이해한다.
2. KBO 팀별 특징과 연고지를 살펴보고 응원할 팀을 고른다.
3. 원하는 팀의 경기 일정과 경기 정보를 찾는다.
4. 경기와 구장의 기본 정보를 확인한다.
5. 팀과 경기별 예매 정보를 찾는다.
6. 응원 문화, 준비물과 관람 팁을 찾는다.
7. 예산과 관람 성향에 맞는 좌석을 추천받는다.
```

## 4. 서비스 원칙

이번 기획에서 중요하게 잡은 원칙은 "정확해야 하는 정보와 설명형 정보를 분리한다"는 것입니다.

일정, 날짜, 장소, 가격처럼 정확해야 하는 값은 정형 데이터로 조회해야 합니다.

반대로 관람 팁, 반입 정책, 예매 절차, 야구 규칙 설명처럼 문서 근거가 필요한 정보는 RAG로 검색할 수 있습니다.

서비스 원칙은 다음과 같이 정리했습니다.

```text
일정, 날짜, 장소, 가격처럼 정확해야 하는 값은 정형 데이터로 조회한다.
설명과 근거가 필요한 정보만 문서 검색 및 RAG를 사용한다.
정보의 출처와 기준 시점을 가능한 범위에서 표시한다.
정보가 없거나 오래되었으면 추측하지 않고 한계를 알린다.
사용자의 필수 조건이 부족하면 Tool을 호출하기 전에 질문한다.
처음부터 모든 기능을 만들지 않고, 하나의 사용자 흐름을 완성한 후 확장한다.
```

이 원칙은 Tool 설계에도 그대로 반영됩니다.

예를 들어 경기 일정은 RAG로 검색하지 않습니다.

경기 일정은 날짜와 팀 조건으로 정확히 조회해야 하므로 정형 DB Tool이 맞습니다.

반면 "사직구장 처음 가는데 뭐 챙겨야 해?" 같은 질문은 문서형 안내와 출처가 필요하므로 RAG Tool이 맞습니다.

## 5. 왜 Agent가 필요한가

이 서비스를 단순 Workflow로 만들면 모든 사용자가 같은 순서를 거치게 됩니다.

```text
경기 조회
→ 구장 조회
→ 예매 안내
→ 응원 안내
→ 좌석 추천
→ 준비물 안내
```

하지만 실제 사용자는 이렇게 묻지 않습니다.

어떤 사용자는 경기 일정부터 묻고, 어떤 사용자는 구장 위치부터 묻습니다.

어떤 사용자는 야구 규칙을 묻고, 어떤 사용자는 예매 방법만 묻습니다.

예시는 다음과 같습니다.

```text
사용자: 다음 주 롯데 경기 있어?
→ 경기 일정 조회가 먼저 필요하다.

사용자: 잠실야구장 위치 알려줘.
→ 구장 기본 정보 조회가 먼저 필요하다.

사용자: 사직구장 음식물 반입 가능해?
→ 구장 안내 RAG 검색이 필요하다.

사용자: 보크가 뭐야?
→ 야구 지식 RAG 검색이 필요하다.

사용자: 오늘 사직 비 와?
→ 구장 기준 날씨 Tool이 필요하다.
```

즉 사용자의 요청에 따라 필요한 Tool과 실행 경로가 달라집니다.

이것이 이 프로젝트를 단순 검색 서비스가 아니라 Agent 구조로 설계한 이유입니다.

Agent의 역할은 모든 일을 스스로 해결하는 것이 아닙니다.

사용자 요청을 해석하고, 필요한 Tool을 선택하고, Tool 결과를 바탕으로 다음 응답을 구성하는 것입니다.

## 6. 핵심 사용자 여정

최종적으로 지원하려는 대표 흐름은 다음과 같습니다.

```text
야구 기본 지식 확인(선택)
→ 응원 팀 탐색 및 선택(선택)
→ 선택한 응원 팀을 사용자 프로필에 저장
→ 날짜 또는 기간 입력
→ 경기 일정 조회
→ 경기 선택
→ 구장 기본 정보 확인
→ 예매 정보 확인
→ 응원 및 관람 팁 확인
→ 좌석 후보 비교와 추천
```

하지만 MVP에서는 이 전체 흐름을 한 번에 만들지 않습니다.

이미 응원 팀이 있거나 궁금한 정보가 명확한 사용자는 중간 단계를 건너뛸 수 있어야 합니다.

그래서 MVP1에서는 온보딩을 강제하지 않고, 사용자가 바로 채팅을 시작하는 흐름으로 잡았습니다.

```text
사용자 첫 메시지
→ 필요한 조건 추출
→ Tool routing
→ Tool 실행
→ Tool 결과 card 표시
→ assistant 기본 응답
```

## 7. MVP1 범위

MVP1의 목표는 완성된 최종 Agent가 아닙니다.

목표는 채팅창에 KBO 직관 관련 질문을 입력했을 때, 백엔드가 필요한 Tool을 선택해 실행하고, 프론트엔드가 Tool 실행 결과를 카드로 렌더링할 수 있는 기본 틀을 만드는 것입니다.

예상 SSE 흐름은 다음과 같습니다.

```text
conversation.created
message.created
tool.started
tool.completed
assistant.delta
assistant.completed
conversation.updated
done
```

MVP1에서 중요한 것은 답변 문장의 완성도보다 계약의 안정성입니다.

Tool이 실행되는지, 실행 상태가 스트림으로 내려오는지, 프론트엔드가 같은 `tool_call_id`의 card를 갱신할 수 있는지가 먼저입니다.

## 8. MVP1 Tool 범위

MVP1에서는 다음 Tool들을 기준으로 잡았습니다.

```text
find_kbo_game
get_stadium_info
get_weather_context
search_ticketing_guide
search_stadium_guide
search_baseball_knowledge
```

각 Tool의 책임은 다음과 같습니다.

| Tool | 책임 | 데이터 성격 |
|---|---|---|
| `find_kbo_game` | 팀, 날짜, 기간 조건으로 KBO 경기 일정 조회 | 정형 DB |
| `get_stadium_info` | 구장 기본 정보 조회 | 정형 DB |
| `get_weather_context` | 구장/경기 기준 날씨와 직관 컨디션 조회 | 외부 API/정형 계산 |
| `search_ticketing_guide` | 예매 절차와 주의사항 검색 | RAG |
| `search_stadium_guide` | 구장별 안내, 반입, 교통, 시설 등 검색 | RAG |
| `search_baseball_knowledge` | 야구 규칙, 용어, 플레이 설명 검색 | RAG |

여기서 핵심은 Tool을 데이터 성격에 맞게 나누는 것입니다.

경기 일정은 RAG로 찾지 않습니다.

날씨도 RAG로 찾지 않습니다.

반대로 예매 절차나 구장 안내처럼 문서 근거가 필요한 정보는 RAG Tool로 분리합니다.

## 9. Chat API와 SSE 계약

MVP1의 채팅 API는 단일 endpoint로 잡았습니다.

```text
POST /api/v1/chat
```

입력은 단순합니다.

```json
{
  "conversation_id": null,
  "message": "다음 주 롯데 경기 알려줘"
}
```

초기 기획에서는 guest-first 흐름도 고려했지만, 핵심은 새 대화와 기존 대화를 `conversation_id`로 구분한다는 점입니다.

응답은 `text/event-stream` SSE로 전송합니다.

주요 이벤트는 다음과 같습니다.

```text
conversation.created
message.created
tool.started
tool.completed
tool.failed
assistant.delta
assistant.completed
conversation.updated
stream.failed
done
```

프론트엔드는 event name을 기준으로 메시지와 Tool card 상태를 갱신합니다.

예를 들어 `tool.started`를 받으면 실행 중 card를 만들고, 같은 `tool_call_id`로 `tool.completed`가 오면 완료 상태와 result로 갱신합니다.

이 구조를 먼저 잡아두면 이후 Tool이 늘어나도 프론트엔드 계약은 크게 흔들리지 않습니다.

## 10. MVP1에서 제외한 것

MVP1은 범위를 의도적으로 줄였습니다.

다음 기능은 제외했습니다.

```text
지도, 대중교통, 자동차 경로와 현장 동선
좌석 검색과 추천
로그인 필수화
응원 팀 프로필 저장
guest conversation의 user account 귀속
외부 reranker
하이브리드 서치
LangChain/LangGraph 전면 도입
운영용 observability dashboard
LLM이 여러 Tool을 반복 호출하며 계획을 수정하는 Agent loop
```

이 제외 범위가 중요했습니다.

처음부터 "진짜 Agent답게" 만들려고 하면 지도 API, 좌석 추천, 사용자 프로필, RAG 품질 개선, 멀티 Tool loop까지 모두 하고 싶어집니다.

하지만 그렇게 하면 아무 흐름도 끝까지 검증하지 못할 가능성이 큽니다.

그래서 MVP1은 채팅과 Tool 실행 기반을 안정적으로 만드는 데 집중했습니다.

## 11. RAG 적용 기준

이번 프로젝트에서 RAG를 아무 곳에나 쓰지는 않기로 했습니다.

RAG 후보로 보는 기준은 다음과 같습니다.

```text
답이 단일 필드가 아니라 설명형 문서에 있다.
사용자 표현과 원문 표현이 달라 의미 검색이 유용하다.
답변에 근거 문단과 출처를 제시해야 한다.
구장, 팀, 문서 종류 등의 metadata로 검색 범위를 제한할 수 있다.
```

반대로 다음 정보에는 RAG를 사용하지 않습니다.

```text
경기 일정과 경기 상태
구장 공식 명칭, 주소와 좌표
날씨 수치와 예보
좌석 가격과 잔여석처럼 실시간성이 중요한 값
예산과 선호도에 따른 결정론적 점수 계산
```

RAG는 편리하지만 만능 조회 방식은 아닙니다.

정확한 값이 필요한 영역은 정형 데이터나 외부 API로 처리하고, 설명형 지식에만 RAG를 사용합니다.

## 12. 단계별 확장 계획

MVP1 이후 확장은 다음 순서로 잡았습니다.

```text
1. MVP1 채팅/Tool 기본 틀
2. 프론트엔드 SSE stream 연결 마무리
3. RAG 평가셋과 검색 품질 개선
4. 로그인과 사용자 프로필
5. 응원 팀 탐색
6. 응원 안내 Tool 분리
7. 좌석 추천
8. 지도·교통 API 기반 동선 Tool
```

이 중 다음 단계에서 가장 중요한 것은 RAG 평가셋입니다.

RAG는 데이터를 넣었다고 끝나는 작업이 아닙니다.

실제 질문을 던졌을 때 기대한 문서가 검색되는지, 검색 결과가 답변 근거로 충분한지를 계속 평가해야 합니다.

## 13. 테스트와 검증 방향

MVP1의 품질 기준은 기능 연결과 계약 안정성입니다.

검증해야 할 흐름은 다음과 같습니다.

```text
새 대화에서 conversation이 생성되는가
기존 conversation에 메시지를 이어 보낼 수 있는가
팀과 날짜가 모두 있는 요청에서 find_kbo_game이 실행되는가
팀이나 날짜가 부족하면 무리하게 Tool을 호출하지 않는가
구장 정보 요청에서 get_stadium_info가 실행되는가
날씨 요청에서 get_weather_context가 실행되는가
RAG 요청에서 검색 Tool이 실행되는가
tool.started와 tool.completed가 같은 tool_call_id로 이어지는가
assistant.delta가 하나의 assistant message로 누적되는가
Tool 오류를 경기 없음으로 잘못 안내하지 않는가
```

이 기준을 만족해야 이후 답변 품질 개선이나 LangGraph 도입 같은 작업을 안전하게 진행할 수 있습니다.

## 14. 정리

이번 기획의 핵심은 KBO 직관 플래너를 "LLM 하나가 모든 것을 답하는 챗봇"으로 보지 않는 것입니다.

정확한 정보는 Tool로 조회하고, 문서형 지식은 RAG로 검색하고, Agent는 사용자의 요청을 해석해 적절한 실행 경로를 선택합니다.

MVP1에서는 최종 완성도를 욕심내기보다, 아래 골격을 먼저 만드는 데 집중했습니다.

```text
채팅 입력
→ Tool routing
→ Tool 실행
→ SSE event streaming
→ Tool card 렌더링
→ assistant 기본 응답
```

이 골격이 있어야 다음 작업인 구장 가이드 RAG, 야구 지식 RAG, 날씨 Tool, LangGraph context 관리 같은 기능을 하나씩 붙일 수 있습니다.

즉 이번 명세는 구현 전에 작성한 설계 문서이면서, 이후 작업들의 기준점입니다.

앞으로의 글에서는 이 명세를 기준으로 실제 데이터를 수집하고, RAG를 만들고, Tool을 연결하고, 대화 context를 이어가는 과정을 차례대로 정리할 예정입니다.
